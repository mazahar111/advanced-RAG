Title: Auto-adjudication process via machine learning
Abstract: An example operation may include one or more of receiving a loan application of a user, extracting a plurality of personal attributes about the user from the loan application, querying a machine learning model via an application programming interface (API) based on the plurality of attributes about the user to identify one or more rules for auto-adjudicating the loan application, determining whether or not to approve the loan application based on the one or more rules identified via the machine learning model, and transmitting notice of the determination to a device associated with the user.

[0033]Example embodiments provide methods, systems, components, non-transitory computer readable media, devices, and/or networks, directed to a host platform for training and hosting a machine learning model for auto-adjudicating a loan application of an applicant (user).
[0034]In the example embodiments, the machine learning model may be a decision tree. The decision tree may include nodes that are assigned conditions/criteria associated with applicants of a loan application. As an example, a first node may be assigned criteria such as an income of more than 90 k but less than 150 k. As another example, a node may be assigned criteria such as a credit score between 620-700. As another example, a node may be assigned criteria such as a number of bankruptcies being less than 2. The number of nodes and criteria is limitless.
[0035]As a result of the training, each node of the decision tree may be assigned historical loan applications that have the criteria assigned to the node. Here, the historical loan applications will include both applications that have been approved and applications that have been denied. The ratio of loan applications that have been approved versus the loan applications that have not been approved may be identified and used to determine a level of purity with respect to the node. For example, if 1000 loan applications have the same criteria as a node in the decision tree, and 850 of the loan applications have been approved, the purity of the node (also referred to as a pocket) is considered 85% (i.e., 850/1000). The purity of each of the nodes may be identified during the training process. This enables the host platform to cherry-pick the nodes with the highest purity to be the rules of future auto-adjudication processes. For example, a purity threshold can be defined by a user/developer. As another example, the purity threshold can be identified by the training process.
[0036]The purity threshold can be used to identify “paths” within the nodes which correspond to rules to be used for auto-adjudicating a loan process. The paths may correspond to a sequence of nodes (i.e., interconnected within the tree) that have a purity above the purity threshold. As an example, a path may include a root node, a leaf node, and one or more intermediate nodes. It is not a requirement that the path have a leaf node. Each node in the path may add another criteria to a rule that can be created by aggregating the criteria together from the sequence of nodes that have the purity above the purity threshold. Each of the rules (paths) identified from the training process can be embedded within the decision tree and used during live execution on newly received loan applications. Accordingly, the decision tree can be used to auto-adjudicate a loan application without human intervention thereby increasing the time it takes for a loan decision to a few seconds (rather than days or even weeks).
[0037]In some embodiments, the host platform may be coupled to a blockchain network which contains a blockchain ledger. The host platform can record the intermediate training steps and the outputs via the blockchain ledger so that they can be audited later. Also, the host platform may record automated decisions made by the trained decision tree. Thus, the steps taken to train the decision tree and the steps used by the decision tree to make an auto-adjudication of a loan can be audited by future auditors.
[0038]The blockchain network may utilize a decentralized database (such as a blockchain) that is a distributed storage system, which includes multiple nodes that communicate with each other. The decentralized database includes an append-only immutable data structure resembling a distributed ledger capable of maintaining records between mutually untrusted parties. The untrusted parties are referred to herein as peers or peer nodes. Each peer maintains a copy of the database records and no single peer can modify the database records without a consensus being reached among the distributed peers. For example, the peers may execute a consensus protocol to validate blockchain storage transactions, group the storage transactions into blocks, and build a hash chain over the blocks. This process forms the ledger by ordering the storage transactions, as is necessary, for consistency. In various embodiments, a permissioned and/or a permissionless blockchain can be used. In a public or permission-less blockchain, anyone can participate without a specific identity. Public blockchains can involve native cryptocurrency and use consensus based on various protocols such as Proof of Work (PoW). On the other hand, a permissioned blockchain database provides secure interactions among a group of entities which share a common goal but which do not fully trust one another, such as businesses that exchange funds, goods, information, and the like.
[0039]This application can utilize a blockchain that operates arbitrary, programmable logic, tailored to a decentralized storage scheme and referred to as “smart contracts” or “chaincodes.” In some cases, specialized chaincodes may exist for management functions and parameters which are referred to as system chaincode. The application can further utilize smart contracts that are trusted distributed applications which leverage tamper-proof properties of the blockchain database and an underlying agreement between nodes, which is referred to as an endorsement or endorsement policy. Blockchain transactions associated with this application can be “endorsed” before being committed to the blockchain while transactions, which are not endorsed, are disregarded. An endorsement policy allows chaincode to specify endorsers for a transaction in the form of a set of peer nodes that are necessary for endorsement. When a client sends the transaction to the peers specified in the endorsement policy, the transaction is executed to validate the transaction. After validation, the transactions enter an ordering phase in which a consensus protocol is used to produce an ordered sequence of endorsed transactions grouped into blocks.
[0040]This application can utilize nodes that are the communication entities of the blockchain system. A “node” may perform a logical function in the sense that multiple nodes of different types can run on the same physical server. Nodes are grouped in trust domains and are associated with logical entities that control them in various ways. Nodes may include different types, such as a client or submitting-client node which submits a transaction-invocation to an endorser (e.g., peer), and broadcasts transaction-proposals to an ordering service (e.g., ordering node). Another type of node is a peer node which can receive client submitted transactions, commit the transactions and maintain a state and a copy of the ledger of blockchain transactions. Peers can also have the role of an endorser, although it is not a requirement. An ordering-service-node or orderer is a node running the communication service for all nodes, and which implements a delivery guarantee, such as a broadcast to each of the peer nodes in the system when committing transactions and modifying a world state of the blockchain, which is another name for the initial blockchain transaction which normally includes control and setup information.
[0041]This application can utilize a ledger that is a sequenced, tamper-resistant record of all state transitions of a blockchain. State transitions may result from chaincode invocations (i.e., transactions) submitted by participating parties (e.g., client nodes, ordering nodes, endorser nodes, peer nodes, etc.). Each participating party (such as a peer node) can maintain a copy of the ledger. A transaction may result in a set of asset key-value pairs being committed to the ledger as one or more operands, such as creates, updates, deletes, and the like. The ledger includes a blockchain (also referred to as a chain) which is used to store an immutable, sequenced record in blocks. The ledger also includes a state database which maintains a current state of the blockchain.
[0042]This application can utilize a chain that is a transaction log which is structured as hash-linked blocks, and each block contains a sequence of N transactions where N is equal to or greater than one. The block header includes a hash of the block's transactions, as well as a hash of the prior block's header. In this way, all transactions on the ledger may be sequenced and cryptographically linked together. Accordingly, it is not possible to tamper with the ledger data without breaking the hash links. A hash of a most recently added blockchain block represents every transaction on the chain that has come before it, making it possible to ensure that all peer nodes are in a consistent and trusted state. The chain may be stored on a peer node file system (i.e., local, attached storage, cloud, etc.), efficiently supporting the append-only nature of the blockchain workload.
[0043]The current state of the immutable ledger represents the latest values for all keys that are included in the chain transaction log. Since the current state represents the latest key values known to a channel, it is sometimes referred to as a world state. Chaincode invocations execute transactions against the current state data of the ledger. To make these chaincode interactions efficient, the latest values of the keys may be stored in a state database. The state database may be simply an indexed view into the chain's transaction log, it can therefore be regenerated from the chain at any time. The state database may automatically be recovered (or generated if needed) upon peer node startup, and before transactions are accepted.
[0044]The example embodiments provide a novel approach to training a decision tree and a novel use of a decision tree in the form of a set of rules that can be queried to auto-adjudicate a loan application. The training process is new in the art of decision trees because it is based on the purity of each of the pockets (nodes) in the tree. As a result, only some of the nodes (and their performance) are considered during execution rather than all of the nodes of the decision tree. As a result, less than the entire tree needs to be loaded and executed thus improving the efficiency of the model execution. Furthermore, the trained model can then be queried via an interface such as an API for approval/denial of a loan. This obviate the need for a human to perform this process.
[0045]FIG. 1A illustrates a process 100A of training a machine learning model to enforce a set of rules according to example embodiments. Referring to FIG. 1A, a host platform 120 hosts a training environment 122 and a live environment 124 (also known as a productive environment). The training environment 122 may include a runtime environment dedicated for training and testing, and which is isolated from the live runtime environment 124. The host platform 120 also access a database 132 of historical loan application data.
[0046]In the example of FIG. 1A, a decision tree model 126 may be trained within the training environment 122. For example, a developer 110 of the decision tree model 126 may access the host platform 120 via a user interface, and configure the training process. The decision tree model 126 may include a plurality of nodes, and edges connecting the nodes. The nodes may be assigned criteria that can be used to auto-adjudicate a loan such as income requirements, credit score requirements, bankruptcy requirements, and the like. During the training, historical loan applications can be pulled from the database 132 can be input to the decision tree model 126 during execution which configures the decision tree model 126. Historical loan applications that have the criteria of a node may be identified and added as a count to the node. Also, an identifier of whether the loan application was successful (e.g., approved by the lender, accepted by the applicant, paid off by the applicant, etc.) The database 132 may also include a blockchain ledger where intermediate training steps, training data used, outputs of the decision tree model 126, and the like, that are generated during the training can be committed to the blockchain ledger.
[0047]The host platform 120 may identify rules from the trained decision tree model 126. For example, a paths of interconnected nodes within the decision tree model 126 and which contain a purity above a predefined purity threshold can be identified as a rule by the host platform 120. The paths may include a sequence of nodes starting with a root node and ending with a leaf node or other node. In between the root node and the leaf node may be one or more intermediate nodes. Each node may have a different criteria. The path of nodes may include a path (plurality of nodes within the tree) or sequence of criteria that can go into making a rule. The sequence of nodes may include one or more nodes for an income level, one or more nodes for a credit score level, one or more nodes for a bankruptcy count, and the like.
[0048]FIG. 1B illustrates a process 100B of generating a decision based on execution of the machine learning model according to example embodiments. Referring to FIG. 1B, the trained decision tree model 126 can be exported from the training environment 122 and imported into the live runtime environment 124. For example, an executable(s) or zip file with the executable(s) may be exported out of the training environment 122 and installed or otherwise deployed within the live runtime environment 124. This process may include modifying address pointers and other information used by the decision tree model 126 to interact with a database 134 for storing loan decision information. In some cases, the database 134 may include a blockchain ledger. Decisions output by the decision tree model 126 may be recorded on the blockchain ledger.
[0049]In the example of FIG. 1B, a loan application can be uploaded to the host platform 120. For example, although not shown in FIG. 1B, the host platform may include an application programming interface (API) which can be called by a software application or other program on a computing device. The loan application may be submitted to the decision tree model 126 via the API. As an example, the loan application may be submitted by a lender or a dealership 144 (such as an auto dealership) that is selling the item to the user. As another example, an applicant 142 may submit the loan application in an effort to pre-process the loan application prior to the sale being finalized. Thus, the user (applicant) can be pre-approved for a loan before the applicant purchases the item.

Referring to FIG. 2B, the transaction flow may include a client node 260 transmitting a blockchain transaction proposal with a security token as described according to various embodiments to an endorsing peer node 281, in 291 and to an endorsing peer 282, in 292. The endorsing peer 281 may verify the client signature and execute a chaincode function to initiate the transaction. The output may include the chaincode results, a set of key/value versions that were read in the chaincode (read set), and the set of keys/values that were written in chaincode (write set). Here, the endorsing peer 281 may determine whether or not to endorse the transaction proposal. A proposal response 292 is sent back to the client 260 along with an endorsement signature, if approved. The endorsing peer 282 may perform the same process as endorsing peer 281 and send back a proposal response 294 to the client 260. The client 260 assembles the endorsements into a transaction payload 295 and broadcasts it to an ordering service node 284. The ordering service node 284 then delivers ordered transactions as blocks to all peers 281-283 on a channel. Before committal to the blockchain, each peer 281-283 may validate the transaction. For example, the peers may check the endorsement policy to ensure that the correct allotment of the specified peers have signed the results and authenticated the signatures against the transaction payload 295.
